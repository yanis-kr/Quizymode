# Uploaded picture operations

This runbook accompanies AC 3.27 and `pictures-v1`. General production cleanup and provider processing are launch decisions, not enabled by this document. The owner must approve the completed picture policy and withdrawal/retention/restore procedure before exposing uploads generally.

## Release gate: ship with uploads off

`Media__UploadsEnabled=false` must be set in the production environment **before** the deploy that contains this epic, and stays set until the owner approves the policy (`pictures-v1`) and this runbook and confirms launch. Verify after deploy that `POST /media/images` answers `503 Media.Disabled`. Turning uploads on is a separate, explicit owner action.

## Admission and data

The server accepts one JPEG/PNG/still WebP file, at most 2 MiB; it stores only normalized WebP, never original bytes or file names. `Idempotency-Key` is scoped to the authenticated owner and a source-byte digest. A changed file with an old key is 409; an active same-key request is 409; a completed retry returns the same asset. Reservations survive restarts, expire after five minutes and permit at most three attempts. Normalization and storage writes have separate bounded deadlines. Ambiguous successful writes reuse the immutable asset/key on retry. A separate durable attempt row charges every actual decode admission, including failed same-key retries; completed successful replays do not consume a new decode attempt. Claims contain a digest, identifiers, times and state, not original data.

Before any multipart parsing/buffering, separate durable transport rows reserve one request and the entire maximum envelope (`MaxSourceBytes +64KiB`) against rolling owner request/byte limits, even for malformed/duplicate/oversized/partial bodies and successful replays. `MaxGlobalIngress=8` spans replicas/restarts under the shared PostgreSQL lock. `IngressReadTimeout=20s` bounds partial reads; active lease is timeout plus30s to recover abandoned processes. Entire envelope counting includes ignored/duplicate parts. `MaxIngressBytesPerDay=44MiB` conservatively charges reserved bytes, not just completed file bytes; received-byte counts are diagnostics only. No failed read refunds the daily reservation. Only counts/timestamps/owner IDs are durable, never source bytes/filenames/prose. Decode claims remain independently bounded: a completed replay consumes transport allowance but no new decode. A changed source under an old idempotency key remains409.

Defaults (`Media` options; the #405 names `MaxUploadsPerUserPerDay`, `MaxRetainedBytesPerUser`, `MaxPendingReviewsPerUser`, `MaxRetainedBytesGlobal` are deprecated aliases): 20 upload admissions/hour, 20/day per owner, a 5000/day global admission ceiling, 20 pending-review items, 20 MiB retained normalized storage per owner, eight active global reservations and a 1GiB global retained-storage ceiling. A reservation conservatively charges the maximum normalized output before decode. Limits are server authoritative; the existing request rate limiter is a second backstop. Removing a form slot does not immediately reclaim storage. A quota rejection is 429 with a stable code; it promises no invented countdown. Upload and attachment/approval/withdrawal/cleanup mutations serialize with a PostgreSQL transaction advisory lock across replicas. This is deliberately conservative for the small workload; monitor lock contention before increasing throughput.

`POST /items` accepts optional `createRequestId` and persists the request digest with the created item. A lost-success retry with the same owner/key/body returns the existing item; different content with the same key is 409. Upload and item identities are independent. JSON import validates every image shape/ownership/readiness before creating an Upload, item or collection; valid media imports are private pending review even for an admin. Same-owner JSON includes safe asset IDs and descriptions; foreign pictures require explicit text-loss acknowledgement and an `omittedPictures` manifest. Seed ingestion accepts curated references only and cannot replace an uploaded attachment.

## Reports and withdrawal

1. Reports require a currently visible item/collection, slot and revision. Anonymous legitimate share viewers may report. Select an enum concern; do not solicit personal data, contact information or prose. Reports alone never remove content.
2. The Pictures tab shows the bounded reports queue. Inspect exact normalized previews and semantic context. A stale revision must be reloaded; do not repeat an old withdrawal against a changed item.
3. **Withdraw picture everywhere** marks the asset unavailable and advances EVERY referring item's revision to Withdrawn in one transaction. Delivery and new attachments fail, approvals become stale, and all item eligibility routes lose that asset's approvals. The action remains available while upload/AI/delivery are disabled.
4. Verify a previously successful dedicated-test URL is 404, recording time, status, cache headers and request route. Repeat direct/collection/owner/anonymous routes where applicable; the target is at most 300 seconds. Already downloaded copies cannot be recalled. Do not screenshot or download suspected illegal material; follow the picture policy's owner escalation procedure.
5. Reversal means a fresh lawful upload and new human review. Never clear a tombstone or restore an approval to revive a withdrawn key.

Reports store daily HMAC pseudonyms instead of raw IP/user-agent/contact information. The HMAC secret stays server-side and is never returned by control endpoints. Reports and completed admission claims expire after 30 days when the cleanup worker runs; disabled cleanup requires an owner-approved retention sweep rather than claiming retention happened. Review audit rows and media tombstones remain for accountability and restore safety; they do not contain the original bytes.

## Cleanup and restore

`Media:CleanupEnabled=false` by default. In production an enabled worker must have `CleanupOwnerUserId` set to an explicitly authorized dedicated test owner's internal ID, or separately approved `CleanupAllOwnersApproved=true`. Do not enable the latter from this epic's test-account authorization. Unknown-owner storage orphans are never deleted in owner-scoped mode. Defaults are seven days for unattached assets, seven days for rejected references and seven days after withdrawal. Current approved/pending references and undecided review references protect assets. A detached rejected picture follows unattached retention. Rejected current references expire only when every referring item is rejected and its decisions are old enough.

The worker runs every 15 minutes in bounded batches. It rechecks references under the same transaction lock, durably commits withdrawal/tombstones before object deletion, then records physical purge. Missing-object delete is idempotent; storage errors retain tombstones and schedule capped exponential retries. Listing always sends `Prefix=normalized/`; keys must match the immutable media-key grammar, and the listing cursor persists across restarts. No raw/quarantine prefix exists because source data is never persisted.

Before granting deletion, apply and test a reviewed IAM policy limited to this private bucket's `normalized/*`, with prefix-conditioned ListBucket; never broaden to the web bucket, ACL/public permissions or arbitrary bucket deletion. Existing deployed principal was independently observed to have Put/Get only; checked-in code/policy candidates do not prove production Delete/List access. Test a dedicated-owner unattached asset and an attached control, missing-object retry, restart and failed deletion before enabling any broader scope.

Back up application state and immutable media together. On restore, preserve/replay the latest asset tombstones and administrative withdrawal decisions before opening delivery. Keep delivery disabled until current references are checked against object existence and tombstones. Restoring an older database must not revive grants. No automated tombstone-clearing restore is supported. A missing object is unavailable, never a reason to fall back to public S3/another authorization route.

## Optional AI assistance

Provider is Gemini `gemini-3.5-flash-lite` via its image-understanding API, consuming exact normalized WebP and bounded question/answer/explanation/alt/attribution/long-description context. All visible and embedded text is untrusted; there are no tools or approval actions. Runtime requires `Media:Advisory:Enabled`, `ProcessingTermsAccepted`, `PrivateContentAllowed` and the independent durable advisory switch. All are off by default. The existing `Gemini:ApiKey` route is used; no fallback, purchase or billing change occurs. Do not treat an existing study-guide key as permission to send private images.

Primary references: [image input formats](https://ai.google.dev/gemini-api/docs/image-understanding), [processing terms](https://ai.google.dev/gemini-api/terms), [pricing](https://ai.google.dev/gemini-api/docs/pricing). Unpaid terms may allow improvement and human review; production private content must stay excluded until acceptable terms, processing region, retention and owner authorization are documented. On 2026-11-05 the official pricing.md entry listed Standard free-tier input/output as free and paid-tier input (including images) at $0.30 and output (including thinking) at $2.50 per million tokens. This does not establish the account tier, privacy consent or a spending authorization. Model/price/terms must be rechecked before enabling; no paid fallback is authorized. The new optional adapter default is the current stable Gemini 3.5 Flash-Lite; existing study-guide routing is unchanged.

Jobs are identified by item/revision/content hash, both asset hashes, provider/model and policy. Refresh reads persisted results and makes no provider call. Default durable budgets are 20 calls/day globally, five/owner/day, one concurrent call. Call and conservative cost reservations are charged durably before dispatch; ambiguous timeout retains the entire reservation. Defaults reserve$0.05/call with$1 global/$0.25 owner daily ceilings; no automatic purchase follows a budget rejection. The reserve conservatively covers bounded two-picture/context input plus1500 output tokens at the documented paid list prices, with margin; it is an estimate, not an invoice or account-tier claim. Provider-reported prompt/candidate/thinking token counts and a price-based estimate are persisted when supplied. Missing usage stays unknown and never refunds an ambiguous call. Changing models/prices requires reviewing the reservation assumption. A job identity is attempted once; outage/schema failure remains pending human review, not an automatic retry or approval. Kill switch is checked before dispatch; result revision is checked before exposure. Output is strict allowlisted categories, finite 0..1 scores and bounded plain reasons. Reasons must not repeat personal data.

Run the lawful synthetic evaluator only under explicit existing-route authorization: `dotnet run -c Release --project scripts/PictureAdvisoryEvaluation -- <output-directory> [fixture-id]`; inject `QM_AGENT_GEMINI_EVAL_KEY` in process memory, never a file. `--offline` creates normalized fixture previews without a key/call. The report contains labels, predictions, class TP/FP/TN/FN/counts and explicit coverage limitations. The small graph/flag/map/concept/history/medical and text-proxy set cannot establish sensitivity to sexual/graphic violence/hate/real personal photos/infringement. Missing representative positive fixtures or live outputs are NOT RUN, never a mock accuracy pass. Human disagreement review and release approval remain required. The corpus supplies semantic/risk cues in question context, so its per-class counts are functional context-rich triage checks, not blind or representative accuracy. Actual owner-authorized 14-fixture run on2026-11-05 made eight requests: seven completed, then HTTP503 high demand; fail-fast left six further fixtures NOT RUN. Preserve those real output/outage artifacts and do not automatically retry or switch billing.

## Metrics and alerts

The registered `Quizymode.Media` meter emits content-free counters: `quizymode.media.uploads` (outcome), `quizymode.media.reports` (enum category), `quizymode.media.withdrawals`, `quizymode.media.cleanup` (deleted/retry/orphan/failure), `quizymode.media.advisory` (Complete/Stale/Unavailable), `quizymode.media.advisory_reserved_usd` and `quizymode.media.advisory_estimated_usd` (estimated amounts, not billing invoices). Do not add file names, URLs, user/item IDs, prompts or provider response text as metric labels. Verify the actual OTLP/Prometheus exported names before provisioning rules; dot-separated instrument names commonly become underscore-separated counters with `_total`.

Concrete candidate alerts: any cleanup failure/retry in 15 minutes (warning, inspect scoped IAM/storage and retry backlog); five advisory Unavailable outcomes in 15 minutes (warning, disable assistance and continue manual review); any withdrawal (informational, verify prior grants within 300 seconds); five reports in 15 minutes (review queue warning). The metrics worker samples pending count, oldest pending age, total retained bytes and delete retries once a minute after a 30-second startup delay. Alert on oldest pending review >48 hours and global storage >80% of the default1GiB budget. Candidate Prometheus expressions live in `infra/grafana/media-alerts.rules.yml`; verify actual exported names and delivery before enabling. These are configuration candidates, not a claim that Grafana rules or contact points are deployed. Root read-only audit found zero rules; only actual provisioning/readback/test notification can establish live alert coverage.

Emergency controls live in Admin → Review Board → Pictures → Picture reports and emergency controls. Upload, delivery and assistance switches are independent. After a switch change, verify actual response statuses and manual review/withdrawal availability. Keep the optional provider off during outages or disputed privacy terms.

## Actual media route and cache verification

The tracked production SPA API URL points directly to the Lightsail container hostname. Read-only observations in this epic found Kestrel API responses without Cloudflare cache headers; the website uses the single CloudFront web-bucket origin and has no media origin. Do not assert that Cloudflare or CloudFront caches current uploaded-media requests. Media remains private behind the API and responds `private, no-store, no-transform`; no signed object URL is exported. Recheck deployment configuration and response headers on release. CDN purge is N/A only when the actual successful media URL demonstrably bypasses those CDNs. If routing changes, configure a no-cache bypass for every item/collection/media route and verify before launch.

Current-reference retention clarification: Withdrawn item references are inactive, including a rejected item's sibling slot after asset-wide revocation. Deleted/historical undecided audit rows remain audit history without leasing object bytes. Approved/PendingReview/other live references (including another owner) and applicable current undecided submissions remain protective. Due decisions must belong to the current rejected revision/reference; a new Withdrawal audit never restarts a rejected sibling's clock. Once no live protection remains, old inactive bytes may be reclaimed at existing asset age eligibility; <=7days is a maximum, not a new mandatory minimum. Direct withdrawal retains its existing DeletedAt/backoff schedule without resetting it. Tombstones commit before object deletion and prevent later attach/approval/import.

Delivery snapshot protocol: first-party requests always send a positive DTO `expectedRevision` to direct or exact collection GET; stale404 must never fall back. Legacy omitted-query clients retain current-slot semantics and cannot claim an image/text snapshot. Empty/zero/invalid provided revisions are400. Recheck this on ordinary/admin/report/recap/print release evidence.
